The Game Engine

Physics and netcode: how a shared game stays fair, and how it stays smooth.

Fair is easy. Smooth is easy. Both at once, over the internet, is the whole job.

Two halves: the referee (fair), then the in-betweens (smooth). The buffer engine is the one deep part, at the end.
The picture first

A football match on the radio

You hear the match a little late. The referee on the pitch already made the call.

  • The referee sees the real match. Their call is final.
  • You hear it half a second later. You still enjoy it.
  • A good commentator fills the gap, so it never sounds like it stops.

In our games, the server is the referee and your screen is the commentator. The commentator is not allowed to invent goals.

Physics

Rules that step, not rules that flow

  • The game moves in ticks: many small steps every second.
  • Each tick, everything moves a little, falls a little and bumps a little.
  • The same start and the same inputs give the same game, every time.
  • So a test can play a whole game with no screen at all, and check it.

A flip book never surprises you. That is a compliment.

Fair

The server holds the true game

Your screen sends

Only what you pressed. Not where you are.

The server decides

It runs the rules and makes the true frame.

Everyone gets

The true frame. Some games send each player only what they can see.

You cannot tell the referee you scored. You can only kick the ball and hope.

One game room is one Durable Object (talk 0). Say "the referee's notebook" again.
The problem

True frames arrive late, and not on time

The internet is a post office. Most letters come fast. Some come late. A few come together.

  • Draw each true frame the moment it lands, and the game stutters.
  • Wait for every frame, and the game feels slow.

Lag is the referee's whistle arriving late. Stutter is three whistles arriving at once.

Smooth

Draw the moments in between

Your screen keeps the last few true frames, and draws smooth moments between them.

  • It stays a tiny bit behind the newest frame, on purpose.
  • So there is always a next frame to slide toward.
  • When a frame is late, the slide simply takes a little longer.

The commentator stays one breath behind the match, so they never run out of words.

The cute specific

The buffer engine: smoothing twice

A new engine in Rust, running as WebAssembly. It smooths in two places, not one.

Two commentators: one at the stadium gate, one in your living room. The referee still has the last word.

This is the one deep part of the talk. Say what it does: a buffer at the edge, close to the player, runs a little ahead of the server's true frames; the screen smooths between what the edge sends. Do not explain how far ahead, how it guesses or how it corrects.
Why two places

The long trip and the short trip

  • The trip from the server to the edge can be long. The edge covers that wait.
  • The trip from the edge to you is short. Your screen covers that one.
  • When a guess is wrong, the next true frame fixes it gently, not with a jump.

Like a relay race. Each runner only has to be good at their own stretch.

What the games prove

The engine in real games

One room, one notebook

Each game room lives in its own small cloud memory.

Only what you can see

In hide and seek, the server never tells you where the hiders are.

A world in pieces

A big map splits into regions. Each busy region gets its own referee.

Headless games

Robots play thousands of games with no screen, to test and to balance.

A cheater cannot read what the server never sent. That is the cheapest anti-cheat there is.

Talk 3, part two

The Twin Sim

The twin engine: the same game rules, written twice, that never disagree.

Two copies. One brain. Constant arguments, settled by a test every time.

The one deep part of this half is the slide on why plain sums.
The picture first

Two cooks, one recipe

Two cooks make the same cake in two kitchens. The cakes must be identical, to the crumb.

  • One cook is very fast. The other is very easy to talk to.
  • You can swap one for the other at any moment, and nobody can taste it.
  • After every cake, a judge compares them. Any crumb out of place, and the kitchen stops.

The fast cook is Rust. The friendly cook is TypeScript. The judge has no sense of humour.

The pair

Two engines that work as one

The TypeScript sim

The rules of the game, easy to read and change. It is the source of truth.

Like: the recipe in the book.

The Rust sim

The same rules in Rust. It runs on a server, on a laptop, or in the page as WebAssembly.

Like: the same recipe, by a faster cook.

Same start, same button presses: same game, tick for tick.

Why two

What the pair gives you

  1. A replay the server can trust. Any copy can play the game again and get the same result.
  2. Thousands of test games. The Rust copy plays robot against robot on every core, to keep the game fair.
  3. A safe fallback. If the Rust copy cannot load, the TypeScript copy plays. The player never knows.

Speed is nice. Agreement is the point.

Where you can see it

A creature brawler on two engines

  • Our creature fighting game plays its fights on the Rust copy, inside the page.
  • Until the Rust copy loads, or if it will not, the fight plays on TypeScript.
  • A robot tuner plays bot against bot in Rust, many fights at once, to keep each beast near even odds.

Seventy-odd folklore beasts, all within a whisker of a fair fight. The jackalope is still smug about it.

The hard part

One tiny difference ruins a whole fight

Computers round numbers. Two engines can round the last digit differently.

  • One wrong last digit in tick 1 is a tiny error.
  • By tick 1,000 the tiny error is a different fight.
  • Fast is easy. Identical is hard.

A butterfly flaps its wings in Rust. A dragon loses in TypeScript.

The cute specific

We do the hard maths with plain sums

Turning, curving and growing numbers usually come from a built-in maths library. Each engine's library can differ in the last digit.

  • So the game does that maths itself, with only add, subtract, multiply and divide.
  • Plain sums give the same answer in every engine.
  • Both copies use the same hand-made maths, written line for line the same.

The calculator in your pocket rounds its own way. So we went back to pencil and paper. Very fast pencil.

This is the "cute specific": the built-in sin, cos and friends may differ in the last bit between engines, so the sim uses its own versions made only of basic arithmetic. Do not go further into how they are built.
The judge

A test plays both copies, every time

A change to the rules goes into both copies in the same change, or the judge says no. The judge does not accept "later".

Not only games

The same idea all over Rusty Buns

  • A music app makes the same sound in Rust and TypeScript, sample by sample.
  • A rigging tool gives a 3D model the same bones in both.
  • Every Rust part in Rusty Buns comes with a TypeScript twin.

The twin sim is the game version of a family habit. The whole family argues the same way.
