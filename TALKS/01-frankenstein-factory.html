The Frankenstein Code Factory

How a place that stores code learned to run itself, copy itself and change itself.

It's alive. It also asks permission before it goes outside.

Open with the picture, not the parts. If someone in the room only remembers one slide, it should be the loop (slide 9).
The picture first

A bakery that bakes its own ovens

Most bakeries buy their ovens. This one bakes them.

  • The recipe book holds the recipes for bread. It also holds the recipe for the oven.
  • The bakers read the book, bake, and sometimes improve the oven recipe.
  • When the new oven is ready, it goes in. The old oven goes out.
  • The head baker tastes everything before it goes in the shop window.

Do not try this with a real oven. Ours is made of software, so the worst case is a burnt test.

Map it as you go: recipe book = codeSplitter, bakers = AI helpers in Agent Office, the oven = the office itself, head baker = the owner.

Part 1 · the recipe book

codeSplitter: every line wears a name tag

Normal code storage thinks in files. codeSplitter thinks in lines.

  • Each line gets its own tag: an id, an author and a history.
  • Three helpers can change one file at the same moment. They do not overwrite each other.
  • It is still real git underneath. Normal tools still work.
  • A merge helper called Mervin joins the work together. Mervin uses rules, not AI. So a merge costs no AI money.

Mervin is not a person. Mervin does have a badge, a track record and strong opinions about tabs.

This is the "cute specific" that is safe to share: line identity as the unit of collaboration. Do not go into how the ids are made or stored.
Part 2 · the borrowed kitchen

Agent Office: a gift, stitched onto our engine

Agent Office was made by WebDevCody and shared under the MIT license. We did not rewrite it. We wrapped it.

  • Their office was a Node server. Rusty Buns turns it into one file for Mac and Linux.
  • We changed almost nothing inside it. Our changes sit at the edges, like stitches.
  • Then we gave it a new skin: the forest grove from our game Druids Curse.
  • Each AI helper now walks around as one of the game's monsters: a skeleton, a void wolf, a swamp creature.

The helpers are working on your code. They are also, technically, haunted.

Credit WebDevCody out loud. The point of "nothing forked" is that we can take their new versions without a fight.
Why "Frankenstein"

Someone else's body. Our engine. Our game's faces.

Stitches are visible on purpose. That is how you know where to unpick them.

Part 3 · the sealed room

The office runs in a box with one door

AI helpers type commands. So we keep them in a sealed room.

  • The box sees only the folders you list. Your other files are not there.
  • It gets only the keys you list. Secrets stay out by default.
  • It can reach only the websites on its list. Any other site makes a card pop up: Allow or Deny.
  • No answer in two minutes means no.

Think of a toddler in a playpen with a laptop. Very productive toddler. Still a playpen.

The trick

The recipe book holds the oven's recipe

codeSplitter stores the code for many apps. One of those apps is the office. Another is codeSplitter itself.

  • So the helpers in the office can open the office's own code, and change it.
  • They can also change codeSplitter, the place that holds them.
  • Nothing goes live until a person reads it and presses the button.

Yes, it is a snake eating its own tail. A careful snake, with code review.

The guard rails

Why this does not end like the movie

  1. A person presses deploy. A helper can write code. It cannot ship it.
  2. Unread code never ships. Not even with the owner's own key.
  3. Secrets stay behind a fingerprint. They unlock only when the owner touches the sensor.
  4. Every helper has a budget. Stuck twice the same way? It stops and leaves a four-line note: done, next, broke, don't.
  5. Every copy lives in a sealed box. It sees only what it was given.

The monster is the tools. The doctor is you. The doctor signs every release.
