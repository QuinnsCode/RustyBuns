# codeSplitter reference

Every feature in detail, how to deploy it, and where the code lives.
The pitch is in [README.md](README.md).

## Features in detail

- **A file is a Durable Object.** It is the only writer for that file, so every edit from every agent lands in one order.
  Ops name lines by stable id, not index, so agents editing different lines never collide.
  Editing the same line is optimistic: an op carries the line's rev, and a stale one gets a 409 the agent retries.
  An edit that depends on other lines (is this variable ever reassigned?) sends `ifRev` and only lands if the whole file hasn't moved since it was read.
- **Branches and merges, by line.** An agent opens a branch (`POST /api/repos/:o/:r/branches`) and edits with `?branch=name`: the first time it touches a file, that file's Durable Object forks a copy of itself, every line id and rev intact.
  Reviewing the branch (`GET .../branches/:name`) shows each file's ops against main as it is now, and any conflicts.
  A merge (`POST .../branches/:name/merge`) is a three-way merge by line id that main's file applies in one batch, each line keeping its author: lines only one side touched merge cleanly, and so does a line or block one side moved and the other edited (the edit, and any lines added under it, follow it), the same new line added at the same spot on both sides (it lands once), a line both sides changed in different words (one re-indents, the other changes an argument), and a list or paragraph both added to (an import, a one-line object or type, a CSS rule line, a sentence: both land, main's first, or in order if the list was sorted).
  New lines both added at one spot land main's first, each block whole.
  A stretch both sides reshaped (lines added or deleted where the other side changed one too) is settled line by line when it can be: each old line paired with its version on each side, those merged as above, and lines only one side added kept whole, so a one-liner both added to with declarations added under it, or one reflowed onto lines of its own, merges.
  Conflicts are a line both sides rewrote in the same words (or one renamed a word the other newly uses; in prose and comments, short and common words like "a" and "it" don't count), one key added to a list two ways, a reshaped stretch that won't settle line by line (two rewrites of one function, or in code an old line one side removed: one conflict for the whole stretch, as git would), and the same line added on both sides in different places in the same block (it would land twice; the same setup line in two new tests is fine).
  Some files merge by their own rules: a lockfile both sides changed is one whole-file conflict (keep a side, then regenerate it), a config key (`.env`, JSON, YAML, TOML) the merge would define twice is a conflict, and in code, lines added right next to lines the other side deleted are a conflict (the deleted lines may be what the new ones use); prose like Markdown is left looser.
  A repo overrides how a path merges in its `.gitattributes` (`src/policy.ts`): git's `merge=union` keeps both sides of a stretch both rewrote (main's first, a line both added once), `merge=binary` or `-merge` keeps one side's file whole, and `codesplitter-merge=lock|keyed|prose|code|union` picks a rule by name.
  `codesplitter-live=free|line|locked` and `codesplitter-leftover=ai|person|ci` say how live edits should go and who settles what the merge leaves (defaults: lockfiles locked and regenerated by CI, config and prose to a checked AI, code to a person); the review shows each file's `policy`.
  Each is settled by its line in `resolve: {path: {line: pick}}`, a pick being `"main"`, `"branch"`, `"both"` (main's lines, then the branch's), `"both:branch-first"`, or `{"text": "..."}` (one or more lines of your own in its place, blamed on you); a lockfile, a doubled config key or code that won't build takes only main or branch.
  The review lists each conflict's `choices`, and for one line both sides only added words to at the same spot, a `suggestion` that keeps both, main's words first: merge with `{"text": suggestion}` to take it.
  A coding agent can write one too (`POST .../branches/:name/conflicts/agent {path, line, harness}`, `suggest_resolution` over MCP): it gets the conflict as git's markers with main's lines around it, main's commit messages to the file, and the branch's agent task or, for a branch from upstream, its upstream commit messages to the file. Its answer is checked: the merged file must parse, and the repo's tests run with it in a throwaway clone (only the tests for that file where the test script is plain `bun test`, `vitest` or `jest`, the whole script otherwise). It comes back as text for you to merge with, so nothing lands on its say-so.
  On the site, a branch with conflicts links from the repo's Branches to its merge page (`#/b/owner/repo/branch`): a card per conflict, the base, main's and the branch's version with their changed words marked and main's lines around it, the picks, Ask for an agent's answer, and what each pick lands as; Merge waits until every card is settled, and a merge refused for code that won't build says why there.
  A browser agent gets the same page as `list_conflicts` and `settle_conflict` over WebMCP.
  Any conflict anywhere merges nothing, and merged code that wouldn't build (a name declared twice by keeping both) is refused, whatever was picked.
  A branch that changes what runs at build or deploy time (`package.json`, lockfiles, `rustybuns.config.ts`, `wrangler.*`, `.rustybuns/`, `alchemy.run.ts`, Dockerfiles, `build.ts`, `vite.config.*`, CI files) says so in the review, every changed line shown, and when the owner's next commit to main would deploy, the merge waits for "I've read the build changes" (`build_ok: true`).
  Branches come from crew and agents, and an agent can be prompt-injected.
  A branch can delete a file too (`DELETE .../branches/:name/files?path=`), text or binary: the review lists it as `deleted`, and the merge deletes it from main and from git there and then (making it again on the branch takes the deletion back).
  A branch can be stacked on another (`POST .../branches {name, parent}`): each file it opens forks from the parent's copy where the parent has one, it waits for the parent to merge first (409, and `POST .../merges` takes them oldest first, so the parent goes first), and when the parent merges, its copies move onto main's files: main gave the merged lines its own ids, so they're matched by text, then the stacked branch's changes go on by the same three-way merge, its lines winning where main changed them too.
  One that won't settle that way stays put, and its merge says which files.
  This is built on the line-op log, not git branches, so blame and live sync work the same on a branch; git hears about it when main is catalogued.
- **Every line knows who wrote it and when.** The op log replays the file at any rev: blame and time travel come free.
  The file snapshots itself every 2,000 edits, so time travel replays from the nearest snapshot, and keeps ten: history reaches back at least 20,000 edits, and the log or time travel before that is a 410 naming the rev history starts at (read the file instead).
  The log comes a page at a time (#719): `GET .../do/log?since=&limit=` answers `{ops, next}`, at most 1,000 ops, and `next` is the rev to pass as `since` for the following page (null at the end).
- **Cataloguing** (a commit) hashes the file with its parent, indexes it for search (FTS5 in the repo's own `RepoSearch` Durable Object, `src/search.ts`) and **pushes the repo to Cloudflare Artifacts** as a real git commit.
  Artifacts only takes writes as a git push, so `src/git.ts` builds the objects and the pack itself (Web Crypto and `CompressionStream`, no git library) and speaks smart HTTP.
  The repo page has a `git clone` line with an hour-long read token.
- **Limits, and a fresh start when git fills up.** Every repo page has a Limits button (and ⌘K "Show this repo's limits", `GET /api/repos/:o/:r/limits`): how much of Artifacts' 1 GB a repo its git holds (measured by a fresh start, plus each push since; until then, what was pushed from here), the 32 MB a file cap, files waiting for git, the 256 KB / 5,000-line cap on opening a file, when a temporary dig goes, and where you stand on each of your rate limits.
  A push that doesn't land isn't lost: the file waits in `git_pending` and rides along with the next push that does.
  When git nears the cap (90%, or a push fails in words that read like a full repo), the repo **starts fresh** by itself on its next commit, or its owner presses Start git fresh (`POST /api/repos/:o/:r/fresh`): git moves to a new Artifact holding only the current files, as one root commit with the very same tree, so `git clone` stays one ordinary repo.
  No line loses anything, because its authors and history live in its file's Durable Object, not in git.
  It copies in steps small enough for one request, each its own push (each step's objects sit on staging commits on the new `main` until the last step moves `main` to the real root commit; staging on `main` itself keeps the Artifact's HEAD there, since Cloudflare points HEAD at the first branch pushed), driven by the page's polls and the hourly cron (up to ten minutes of steps a run); commits meanwhile wait and land after.
  The old Artifact is kept, history and all, until the owner deletes it from the panel.
- **Live, fast sync.** Edits go over the file's WebSocket and are acked; every open page gets the exact applied ops and patches itself in place (a gap in revs means a refetch).
  Presence shows who else has the file open.
- **Levels.** Well-loved repos imported: small libraries (mitt, clsx, Ky, Zustand, Hono, Express, Preact), Cloudflare's own open source (Actors, Containers, PartyKit, Cap'n Web, workers-rs, Sandbox SDK, Pingora, Agents, workerd and more), and the stack this app is built on (RedwoodSDK, Effect, React, Alchemy, Bun).
  They're imported into Artifacts shallow (depth 1) and read-only.
  Cloudflare's import stops at 40 MB even at depth 1, so a bigger repo (a level like Alchemy, or a GitHub dig) comes in from GitHub's tarball instead, its tip pushed as one commit with the same tree; past about 64 MB packed, or past Artifacts' repo size limit (Bun, Alchemy), a level is kept in R2 instead: its text files packed into ~8 MB chunks, each folder's entries in D1's tree cache, each read a ranged R2 get through the Cache API.
  A swarm digs those: one call lists the tip's tree, the files split into parts of about a chunk, and each part is a message on the `LEVEL_DIGS` queue, eight running at once (its `maxConcurrency`), each fetching its files raw from GitHub and writing its own chunk; the last part in writes the trees.
  Every import runs off that queue, so it carries on after the admin's page closes, and the level's row counts the parts in.
  Those levels browse and play like any other but have no git, so they can't be forked here (the desktop's local git takes any size).
  An admin imports each one, so a level costs nothing until then.
  The home page scrolls slowly through them.
  Browse any of them; fork one into your own excavation to dig.
  A file only becomes a Durable Object when someone opens it, and a catalogue pushes only what changed on top of the parent tree, so editing one line of a big repo costs one blob, a few trees and a commit.
  Git trees are cached in D1 forever (they're named by hash).
- **Dig it up = fork it.** Digging up a level, or any public GitHub repo (from your journal: type `owner/name` or pick from your own list), clones it into a git repo you own: a bare repo on this machine on the desktop, Cloudflare Artifacts on the edge.
  The dig box (home page and your profile) searches GitHub, or takes anything you copied there: a page URL, a remote, a `git clone` or `gh repo clone` line.
  A folder's URL (`github.com/QuinnsCode/RustyBuns/tree/main/apps/example`) digs up just that folder, at that branch, as the root of a repo named for it (#381): it comes from GitHub's tarball with everything else left out, so the rest of the repo never lands in git (`{repo, path?}` names the folder too).
  Only its Dig it up button digs: Enter in its fields doesn't, so picking one of your repos and a stray Enter can't clone it (#443).
  Nothing else digs either: no page load, palette command or seed does.
  A visitor's dig is temporary, so nobody's experiment runs up the bill: it lasts a day, and once `DIG_CAP` digs (default 20) are live the oldest goes first, rows, file Durable Objects and git together.
  Admins' digs keep.
  The repo and every file say where the fork came from and at which commit, and each line you mod is marked; untouched lines are blamed on `upstream`.
  GitHub never hears about any of it.
  Your repo list comes from a `GITHUB_TOKEN` secret, else your GitHub sign-in, else the GitHub CLI (`gh auth token`) on the desktop.
  Private GitHub repos dig up on the desktop: local git clones them with that token, passed to git for the one clone and never written into the repo.
  On the edge they show greyed out, because Cloudflare Artifacts imports public HTTPS remotes only.
  A dug fork listens to its upstream (#870), on the edge too: every hour, and when its page opens, it asks git's ref list on github.com whether upstream's branch moved past the fork's commit (no API call), and only then GitHub's compare API for how many commits, with the owner's token when there is one.
  The About panel's Upstream section says "N new upstream commits", and **Take them** opens what upstream changed as a branch (`upstream-<sha>`): each changed file with upstream's text, merged into main's live lines where those moved on too (upstream wins where both touched the same lines), new files new and deleted ones deleted, binary ones skipped.
  Review and merge it like any other; the fork then stands at upstream's tip.
  `GET /api/repos/:o/:r/upstream`, `POST …/upstream/hear|take`, `src/listen.ts`.
- **Public or private repos.** A private repo you can't see answers 404, in search too.
  The owner can delete a repo here, typing its name back to confirm (`DELETE /api/repos/:o/:r?confirm=:r`): its rows, its files' and branches' Durable Objects, its cuts, shares, logs and settings, and its git go together, as an expired dig's do.
  GitHub never hears, and a stack it deployed stays up.
- **Share some lines, not the repo.** Select a range (click a line number, shift-click another) and share it: a live link to just those lines that follows them by id as the file changes, and works from a private repo without opening anything else.
  GitHub's permalinks freeze a commit and need the whole repo public.
  Revocable by whoever shared it or the owner.
- **Private lines in a public repo.** Select some lines and make them private: only the repo's crew (owner and collaborators) reads them.
  Everyone else gets a placeholder in the same place (the line's id and number stay, its text is blank): on the file page, in blame and time travel, on the live socket, in shares, playlists and branch reviews.
  A commit pushes the blank line to git and indexes it blank for search, so the remote never holds the real text; walls in the game come from git, so they're blank too.
  Privacy follows the line by id, so editing it keeps it private, and branches hide the same lines.
  Marking the first private line gives the crew a second git remote (an `owner--repo--crew` Artifacts repo, forked from the first) that every commit from then on pushes with the real text, after one commit that fills in lines already pushed blank (retried on the next commit if git's away); the repo page's Clone button hands the crew that clone line too, and previews, deploys and dependency fixes clone from it.
  Everyone else's clone gets the public text.
  Text already pushed before you marked it stays in git's history, so treat a leaked secret as leaked.
  `POST /api/repos/:o/:r/do/private?path= {lines: [ids], private}`.
- **Mirrors: Git going when git stops going (desktop).** Tick "keep it in sync" in the dig box and the repo becomes a mirror of the real one: GitHub, GitLab, or any git URL this machine can reach (`POST /api/mirrors {url}`, with this machine's own credentials: the GitHub token digs use, else git's credential helper or ssh keys).
  Every 5 minutes, and right after each commit, it fetches upstream's branch into the local bare repo, takes what's new (a fast-forward, or a merge commit made with `git merge-tree`, nothing checked out), lands it in any file open here as line edits by `upstream`, merged into live edits, and pushes back what upstream doesn't have yet.
  It never force-pushes.
  Commits go up as this machine's git `user.name` and `user.email`, with a `Co-authored-by` trailer when a handle like `agent-claude` made them.
  When upstream doesn't answer, the Upstream panel on the repo page says it's down and since when, with how many commits are waiting.
  Edits, commits, branches and agents carry on as usual, it tries again (backing off to every 15 minutes), and once upstream answers it catches up by itself.
  If both sides changed the same lines it stops at a clash and moves nothing until the owner picks Keep mine or Take upstream's for those files.
  If upstream rewrites its history (a force-push), it stops at rewritten until the owner picks Re-base on upstream (this copy's own commits replayed on upstream's, then pushed as a fast-forward) or Take upstream's (they're dropped).
  A repo with private lines pulls but doesn't push (its git holds them blank), unless the owner pushes the crew's copy: then that git, real text and all, is the one kept in step, and the repo's own git takes upstream's changes file by file, never its commits, with private-lined files left as they were.
  A mirror never starts fresh.
  Branches go both ways on asking: Push upstream on an open branch sends it up as a real git branch (one commit on main's tip with the branch's files, building on what went up last time and merging main in when it moved, so upstream only fast-forwards), and the Upstream panel lists upstream's other branches with Open here, which makes a codeSplitter branch of what that branch changed (pushing it again goes back to the branch it came from).
  After that each sync follows them: an open branch takes its upstream branch's new commits (Pull upstream does it now, and a push takes them in first, so it never writes over them), and once a branch merged here is committed and upstream's main holds all of it, its upstream branch is deleted, unless somebody added to it since.
  Files deleted upstream are deleted on the branch too, and a file the branch deleted goes from the git branch it's pushed to.
  Binary files come over too (#446): a branch can't hold their bytes as lines, so its row keeps the git blob upstream's branch has (pinned under `refs/branch-blobs/` so a gc keeps it), the review lists it as binary and changed, merging writes it into main's git (and upstream's at the next sync), and a push puts it in the branch's tree.
  It can't be opened as lines on the branch (415).
  `GET|POST /api/repos/:o/:r/mirror`, `GET|POST /api/repos/:o/:r/mirror/branches`, `POST /api/repos/:o/:r/mirror/branches/:b/pull|push`, `src/mirror.ts`.
- **Local out, GitHub in: which side leads (desktop, #464).** A mirror is GitHub-first by default: each sync hears from upstream, then pushes.
  In the Upstream panel, **Make this copy the source of truth** (`POST /api/repos/:o/:r/mirror {primary: "here"}`; `"upstream"` switches back) flips it: the bare repo in `~/.codesplitters` leads and upstream is its backup and the trigger for its Actions.
  A sync with commits waiting pushes them first, before fetching anything, and only fetches and merges when upstream moved too (the push is turned away, never forced).
  A clash still stops and asks, with Keep mine offered first.
  The panel says how many commits behind upstream is and as of when, so with the app closed you know what GitHub has: everything up to the last push.
  If upstream is down, nothing stops.
  **Your own tools use it as a remote:** the Clone button's popover has a `git clone` line (read token, an hour) and, for the owner on the desktop, a **Push back** line, `git remote add codesplitter http://127.0.0.1:…/__rb/git/codesplitters/<owner>--<repo>.git` with a day-long write token (tokens live in memory, so a restart means copying a fresh one), served by the desktop's `git http-backend`.
  Make it a terminal's, an editor's or Agent Office's `origin` with GitHub as a second remote; what you push reaches upstream on the next sync.
  Not offered for a repo with private lines (its git holds them blank).
  A push reaches the files open here as lines too (#773): when one is opened or committed, and at each sync, the commits since the app last saw main (`repos.git_seen`) land in them as your edits, so the next commit here keeps what you pushed.
  A push lands as it arrives (the desktop's git server tells the app), so a page left open sees the pushed lines live.
  A file with no edits since its last commit is committed as pushed; one with edits not committed yet gets the push merged in.
  Where both touch the same lines, or lines right beside each other, it's a clash (#788): the edits here stay, the file page says so (live, on a page already open), and its commit waits (409) till the owner picks **Keep mine** (the next commit writes them over the push) or **Take pushed** (`POST /api/repos/:o/:r/pushes {path, take: "mine" | "pushed"}`).
  Making the file's lines match the push by hand settles it too.
  The app starts watching a repo's git when the repo is made, dug up or mirrored, so a push before its first commit here lands as well.
  **Worktrees:** `POST /api/repos/:o/:r/worktrees {branch, from?}` makes a real checkout with `git worktree add` off the bare repo, under `~/.codesplitters/.worktrees/<owner>--<repo>/`, for git branch `branch` (started off `from`, default main), and `{sha}` makes one detached at a commit for a check run.
  Commits in a branch's worktree land on that branch in the repo's git.
  The default branch never gets one, since the app moves it by itself.
  A run's worktree goes when it's removed (`DELETE .../worktrees/:name`) or after a day, a branch's once main holds the commits it made (or the branch is gone), and one with uncommitted changes stays.
  Every sync and every `GET .../worktrees` cleans up, and deleting the repo removes them all.
  `src/worktrees.ts`.
- **Beam: a branch's stack, cleaned up and handed over.** `POST /api/repos/:o/:r/beams {branch, kind?, onto?, title?, message?, to?, keep?, drop?}` takes git branch `branch` (pushed with the Push back remote, or made in a worktree) from where it left main, and leaves out the noise, each with why: a lockfile the repo doesn't use, lockfile churn with no `package.json` change, `node_modules/` and tool caches, build output the branch added, OS and editor leftovers, and env files (`keep` and `drop` override, by path).
  What's left goes on main's tip, or with `onto: "upstream"` on a GitHub fork's upstream tip (a plain read-only `git fetch`), by `git merge-tree` with no checkout, and is squashed into one commit: the stack's author if it had one, else this machine's git identity with the others as `Co-authored-by`, the title given or the first commit's, and the stack's subjects as the body.
  A 409 says what clashes, or that nothing's left once the noise is out.
  With `kind: "codesplitter"`, `branch` is a codeSplitter branch instead: its files as they are now, laid on main's tip the way a push upstream lays them, are the stack, cleaned up and squashed the same way (by this machine's git identity, whoever opened the branch as `Co-authored-by`).
  That's how an agent hands its work over as one commit: the MCP server's `beam_branch` and `get_beam` tools are these routes.
  A codeSplitter branch stacked on another beams as a commit per branch, in order: the bottom branch's files on main's tip, each next one's over it, the title given going on the top one (`stack` lists them, and the patch has them all).
  A stacked branch's copy of a file made before the branch under it changed that file would take that change back out, so the beam refuses it with `clash`.
  The commit is kept at `refs/beams/<id>` and checked like a pushed branch.
  `GET /api/beams/:id` is the beam and its diff for anyone with the link, `GET /api/beams/:id/patch` is `git format-patch`'s output for `git am`, `to` puts it in that handle's inbox (`GET /api/me/beams`, shown on the feed), and `DELETE /api/beams/:id` withdraws it and drops the ref.
  A repo with private lines can't beam (its git holds them blank).
  Nothing goes to GitHub.
  On the hosted site there's no git to run and no git branches, so `kind` defaults to `codesplitter` there and a beam goes onto main only, as one commit (`kind: "git"`, `onto: "upstream"` and a stacked branch are a 501, and `GET .../beams` says `hosted: true`).
  The Worker's own git (`src/git.ts` `push`) lays the branch's files on main's tip, with the noise left as main has it, and pushes that as one commit to `refs/beams/<id>` on the repo's Artifacts remote, by whoever beams it with whoever opened the branch as `Co-authored-by`.
  The diff and the patch are written in JS from both sides' blobs (`src/patch.ts`), byte for byte what `git diff` and `git format-patch` print, so `git am` takes the patch the same way.
  `src/beam.ts`.
- **Cut: some lines out, run, shared, merged back.** Select lines and press Cut (`POST /api/repos/:o/:r/cuts {pieces: [{path, from, to}]}`): the cut is those lines plus what they use: the file's imports and declarations they use, and, following relative imports into the repo's other files, the declarations they import and what those use in turn (packages aren't followed).
  Add more ranges for anything else you want in it, like a test that covers them.
  It's a branch, `cut-<id>`, whose files start as just those lines with their ids and revs, so the cut page edits them like any branch and Merge into main is the same line-by-line merge; lines that were never in the cut are left alone.
  Run tests (`POST /api/cuts/:id/run`, the repo's owner) runs `bun test` on the cut alone, on the desktop or in the agent sandbox's container for admins on Cloudflare, and marks each test's line pass or fail in the gutter, plus any cut line a failure's stack points at.
  Share hands out `/api/cuts/:id/share`, whose card (`card.png`, drawn in the Worker with no image library) shows the code and its result when the link unfurls on X, and a Post to X button.
  The card is set in DejaVu Sans Mono; pick Geist Mono, the app's own code font, in the Share panel (`?font=geist` on the share link).
  `scripts/card-font.ts` rasterizes another monospace font into the card's format.
- **Give a coding agent a task on a file (super experimental, run at your own risk).** On the desktop, the repo's owner presses Agent on a file page, picks claude, codex, pi or opencode (whichever CLIs are installed), and types a task.
  The CLI runs on this machine with its own login, its edit is diffed into line ops, and the lines land live, blamed on `agent-<name>`.
  Owner only, because the CLI runs as you and can run shell commands.
  On Cloudflare the Worker can't run them, so the button says so unless hosted agents are on (below).
  `bun agent.ts` does the same from a shell.
  **From a phone**, the repo's Phone button (`#/m/owner/repo`) puts it in one column: start an agent on a file, see every run's task and how it's going, and review and merge the repo's branches.
  **Stop it, or tell it something.** Each running agent's card has Stop: its CLI is killed (a hosted run's container destroyed within a couple of seconds), nothing more it does lands, and its claim on lines is lifted.
  With a crowd going, the Agents panel stops them in bulk: all of them, one harness's, or the ones holding the selected lines (`POST /api/repos/:o/:r/agents/stop {ids?, path?, harness?, lines?}`).
  A running CLI can't take messages, so "tell it something" (`POST .../agents/:id/notes {text}`) goes into the prompt of its next run: when this run ends it goes round again on the file as it is, with every note so far (up to 5 extra runs).
- **Rusty Buns fit.** Every repo page says how easily `rustybuns init` could ship the repo as a desktop binary, a Worker and a server: ready, likely, needs work or poor, with the reasons.
  It reads the top level, `package.json` and any vite config, and asks the CLI's own detector (`@rustybuns/cli/fit`), so the two never disagree.
  Frameworks `init` doesn't infer yet (Next.js, SvelteKit, React Router / Remix, Nuxt) link to the issue tracking them; `node:http` servers, native addons and monorepo roots pull the verdict down.
  `GET /api/repos/:o/:r/fit`.
- **The dependency doctor.** On the repo page the owner turns it on (on up to 10 of their repos) and tunes it: how often (6 hours to a month), up to which level (patch, minor, major), how old a release must be (3 days by default, since a bad or hijacked release usually gets pulled within days), and what never to touch.
  It only proposes a version the current range doesn't already allow, so the lockfile's own updates aren't churned.
  It checks every workspace's package.json too, and asks the registry the repo's `.npmrc` names (per scope or for everything), with tokens from the owner's own `~/.npmrc` on the desktop, each sent only to its own host.
  What's worth taking lands on a branch, `deps-<date>`, edited by `agent-deps` and ready to merge, with the lockfile to match: the repo's lockfile picks bun, npm, pnpm or yarn, and on the desktop it is regenerated in a throwaway clone with install scripts off.
  With tests on (the owner's choice, since it runs the repo's own code), each update is first installed and tested in a throwaway clone that is deleted afterwards: a temp dir on the desktop, or on Cloudflare a fresh `AGENT_SANDBOX` container per try, for the site's admins only (it's there only with hosted agents on, `CODESPLITTER_AGENTS=1`, and bills container time), where git, the install and the tests run as a user apart from the agent CLI's, who can't read the agent's logins (#646); if they break together, each is tried alone and only the passing ones go on the branch.
  The owner can also pick a coding agent (claude, codex, pi or opencode) to fix an update that broke the tests, on the desktop: in the same kind of clone, with the update installed, it gets the failing output, the package's changelog, the repo's commits that touched the package and where it's used, and patches as many files as it needs; the tests run after each try, up to the owner's limit (3 by default).
  A fix that passes lands on the same branch, blamed on `agent-<harness>`; one that doesn't is left out with its last output.
  That fixer is one step of the **on-fail chain** (#861), which the owner builds from icons on the repo page, ordering and toggling them (`on_fail`, `["fix"]` by default): 🔁 retry the update, in case the break was a flake; 🤖 the fixer; 🔎 the fixer told to search the web for known breakage first (claude only, with its WebSearch tool, which runs on Anthropic's side so a container needs no more hosts); 📌 hold the release back, off the branch and skipped by later runs until the owner clears it from the held list; ↩️ roll back to the newest release one level smaller that passes (a major tries the newest minor, then the newest patch; a security fix is never rolled back); 🔔 email or notify the owner, once per release.
  Each update's chain stops at the first step that works and is capped as a whole: tries (test runs plus agent tries, 6 by default), minutes (30), and dollars of AI ($2), which counts what claude's JSON answer says each try cost and is checked before each try; pi and opencode report no cost, so they aren't counted.
  The report shows each step's icon with ✓, ✗ or – (skipped, with why), so it says which step settled each update or that the chain gave up.
  The owner can also **rank the packages they care about most** (#862), dragging them into order on the repo page (`rank`, up to 20, highest first), so a clash is settled by rule rather than by luck.
  Peer ranges first, before anything installs: each ranked update, highest first, keeps its target, and a lower one in the same package.json whose target falls outside the higher one's `peerDependencies`, or whose own peers don't take the higher one's target, is re-picked to the newest release that fits both and passes the doctor's other rules (level, minimum age, held back), or else stays where it is (`yielded`).
  Ranges read the way npm reads them (`||`, `^`, `~`, comparators, `18.x`); one it can't read counts as a fit.
  Then, with tests on, updates that each pass alone but break together are added in rank order, each kept only if it still passes with the ones above it; the unranked ones go on together after them, or are all left out, as before.
  A security fix never gives way, and unranked packages impose nothing, so with no ranking a run works as it did.
  The report says what each one gave way to and why.
  "Bring these up, solve around them": `POST …/deps/run {rank}` ranks for that run alone, leaving the saved ranking as it is, and the report says so.
  With **previews** on too (`preview`, off by default, #864, since it costs deploy time), what passed the tests is checked against a real deploy before it goes on the branch: the same preview deploy the owner starts by hand, with the branch's files laid over the clone, deployed to its own `preview-<id>` stage, checked to answer without a 5xx, and destroyed; never a real stage, since only a person ships.
  Without tests the deploy is the whole check.
  If the preview fails, each update goes up alone to find the one that broke it, that one goes down the on-fail chain (whose retry and roll back then have to pass the tests and a preview, and whose fix has to pass a preview after the tests), and what's left goes up together once more.
  Each preview counts against the owner's preview-deploy rate limit and is logged with their previews, by `agent-deps`; one that can't go (over the limit, or out of the run's time) keeps what it would have checked off the branch, for the next run.
  Previews run on the desktop app, with its logins.
  **🪏 Digs** (#863, `digs`, up to 10, one per package): the owner names a future release of a dependency to watch for: `major` (the newest release of the next major line), a dist-tag (`beta`, `next`, `rc`, read from the registry's `dist-tags`) or an exact version.
  Each run looks for it, past the level and the ignore list since the owner asked for it by name, and once it's out tries it in the throwaway clone on top of what passes (in place of that package's own update), down the on-fail chain if it breaks (↩️ skips a dig, since the owner asked for that release).
  The report shows each dig as waiting, already in the range, held back, or out with how its tests went, and the owner hears once when one is first tried.
  Tries need tests on.
  With 🧺 "take it when it's green" on, one that passes (or that a fixer got through) goes on the branch, once it's as old as the minimum age; a prerelease is pinned exactly, a release keeps the range's `^` or `~`.
  A fix to a dig that isn't taken stays off the branch.
  Every run also asks [OSV](https://osv.dev) (GitHub's and npm's advisories) whether the version each range starts at has a known vulnerability.
  A vulnerable one is moved to the first release that fixes it, past the level and the minimum age, since the advisory and not the release says which version is safe, and raising the range makes every install take it whatever the lockfile held; the update says which advisories it fixes.
  One with no fixed release yet, or on the ignore list, is listed in the report as exposed.
  If osv.dev can't be reached the run goes on without it and says so.
  It runs from the Worker's hourly Cron Trigger (`crons` in `rustybuns.config.ts`), which Rusty Buns runs as a minute timer on the desktop.
- **The supply-chain watch** (`src/watch.ts`, #614).
  The same hourly cron polls each agent platform's status page (Anthropic, OpenAI, GitHub, npm and Cloudflare, at `/api/v2/status.json`) and keeps one line each; one that doesn't answer reads unknown.
  It also reads OSV's npm list of changed advisories (`modified_id.csv`, newest first) down to where it stopped last hour, at most 100 at a time, oldest first, and keeps every malicious-package advisory (`MAL-…`, from the OpenSSF malicious-packages feed); a withdrawn one is dropped.

  A sweep that runs out of time picks up where it stopped next hour.
  The repo's owner sees its hits, and the status lines, in the Dependencies section; `GET /api/watch` gives the status lines, and your repos' hits.
  Optional, and off unless the deploy sets `CODESPLITTER_WATCH_NEWS=1` (binding `WATCH_NEWS` and `ANTHROPIC_API_KEY`): once a day the cron asks Claude (Opus 5.5 at low effort, with web search, at most 5 searches) for the past week's news of compromised npm packages, and keeps each incident whose link was one of the search's results, for 30 days.

- **A CLI.** `bun cli.ts` (`apps/codesplitter`) is the same tools as commands, for an agent that would rather run a shell command than speak MCP: `bun cli.ts tools`, `bun cli.ts help read_file`, `bun cli.ts read_file --owner ryan --repo lab --path a.ts`, `--body JSON` (or `-` for stdin) for the ones that take one.

- **The game.** Every repo is a level of a first-person game (`play.html`): you're in the backrooms of the codebase, folders are rooms, files' lines are pasted on the walls, and they tear off and come at you as paper birds and wacky waving tube men.

**Rate limits** (`src/limits.ts`) cap what costs money or invites abuse: sign-ins and new accounts per IP, and per handle digs (Artifacts imports), GitHub lookups on the site's token, code search, new repos, files, branches and webhooks, fresh starts, live line edits, commits (Artifacts pushes, branch merges included), shares and collections, hosted agent runs, preview deploys, hosted deploys (the Deploy button), and dependency-doctor runs started by hand.
Two rules are site-wide budgets that count everyone together, admins included, since what they cap is the site's bill: **hosted runs** (coding agents, conflict agents and feed digests on the site's API keys, 30 a day) and **container minutes** (container checks, 600 a day, about $8 a month at worst).
A hosted run is also stopped at its 15-minute deadline, however many times its CLI has gone round.
Each counts in fixed windows in D1, and a request over its cap gets a 429 with `retry-after`.
Line edits count the same whether they're POSTed or sent over the file's WebSocket: the Worker works out who a socket counts as when it opens, and the file's DO counts each edit, answering one over the cap with a `nack` that carries `retryAfter`.
Only requests from the internet count (Cloudflare stamps them with `cf-connecting-ip`), so the desktop and the Worker's own calls never do, and admins are never limited.
Admins tune each rule on the rate limits page (the gauge in the top bar, `#/admin/limits`; `GET|PUT /api/admin/limits`): its cap, its window, and what happens to a caller over it.
Under each rule is what callers actually got: their count per window across every window the sweep still keeps (about the last day), as low, median, mean, p90, p95, p99 and worst against the cap, and how many caller-windows went over.
**Reject** answers 429, **log** lets the request through and notes it, and **flag** lets it through and lists the caller at the top of the page.
Digs, preview deploys and doctor runs can also **queue**: the request waits in a D1 line (`limit_jobs`) and answers 202 with the caller's place and about when it runs, and once their window has room it's replayed as them, when the page polls `GET /api/jobs/:id`, or, with nobody polling, when its message on the `JOBS` Cloudflare Queue comes due (each queued request sends one, delayed until its window ends; the hourly cron sweeps up any a message missed).
The replay answers as the request would have (a preview's run, a doctor's report or `{running}`), and the page goes on polling the run itself.
The line holds one window's worth.
A caller who leaves the page finds their queued requests on their profile (`GET /api/jobs`): waiting ones with their place in line, finished ones linked to the repo they made or showing the error they hit, and the top bar shows a count while any are waiting.
Line edits and sign-ins can't queue: a queued edit would come back a conflict.
Nor can hosted deploys: one replayed while another runs would only get a 409, so their rule flags callers over the cap by default instead of rejecting them.
The page shows this window's hits and callers per rule, plus a week's log of each time a caller first went over in a window, each with a reset (`POST /api/admin/limits/reset {who, rule?}`) that clears their counts.
The hourly cron clears windows that have ended, and log entries and finished jobs older than a week.

### Deploying (Cloudflare)

`rustybuns deploy` owns the live site: Alchemy took over the wrangler-made Worker `codesplitter` and D1 `codesplitters-db` on 2026-10-09 (`targets.edge.adopt`), Durable Object storage intact.

**Releases go through `scripts/release.ts`.** The owner runs `zsh ~/release-codesplitters.sh` (a copy of `scripts/release-codesplitters.sh`, which each run refreshes from main, so a fix to it can't sit unused in the repo), which puts a release worktree of the agent-office clone on `origin/main` and hands over to it.
It fixes what it can (a locked 1Password, an expired wrangler login, Docker not running, the `wrangler.jsonc` and `.env.schema` that plan regenerates, main moving while you read) and stops on anything that could lose data or cost money: a plan row that deletes, replaces, unbinds or makes something, and the CLI's own warnings (a data delete, state under an old app name).
It always plans before it deploys, says so up front, and pings when a y/N is waiting (the terminal bell and a macOS notification with a sound), since the deploy question is the step that gets left.
`--checks` lets the first `CI_RUNNER` through and remembers that checks are on; `--move` is the codesplitters rename below; a plain release that finds it hasn't run yet (the state under the old app name, or a plan whose only risky rows are the five renames) offers to run it there and then.
Its checks run against plans as `rustybuns plan` really prints them (Alchemy's rows through Effect's `[time] INFO (#1):` log prefix, the owner's own run among them) in `test/release.test.ts`, so a release fix is a PR, not a hand edit.

**The codesplitters names move together (#809).** The config names the D1, queues, R2 bucket and Vectorize index `codesplitter-*`, and the app (which names the Alchemy state) `codesplitter`.
On Cloudflare a rename replaces a resource: Alchemy makes the new one, or adopts it when it's there already, then deletes the old one and its data.
So `scripts/move-resources.ts` copies first: it exports `codesplitters-db` into a new `codesplitter-db` (keeping the `.sql` in `.rustybuns/moved`), copies the bucket's objects, checks the old queues and index, and moves `.alchemy/state/codesplitters` to `.alchemy/state/codesplitter`.
Run it without `--copy` to see what it would do.
Then plan, which warns that each one is renamed, and deploy straight away with `--allow-delete` (a deploy that renames one without it is refused, and so is one whose state is still under the old app name).
`release-codesplitters.sh --move` does it in that order, copying only once you've said deploy, so the copy can't go stale while the question waits; a `codesplitter-db` left by a run that stopped before deploying is deleted and copied again, but only while the live Worker is seen reading `codesplitters-db`.
The Artifacts namespace keeps the name `codesplitters`, since every repo's stored remote names it (#823), and the desktop keeps its data in `~/.codesplitters`, moving its `codesplitters-db.sqlite` and queued messages to the new names itself (`renamedFrom`).
Its state is shared by every worktree of a clone (`.alchemy/state` links into the clone's `.git/rustybuns/alchemy/`), so deleting a worktree doesn't lose it, but a different clone, or a new stage (`--stage`, `$ALCHEMY_STAGE`; the default is `live_$USER`), starts empty.
With an empty state, `plan` says `create` for the Worker and D1, and says first that those creates are adopts: the deploy takes over the live ones by name rather than making new ones.
Anything else it marks `create` is really new.

**D1 has two migration ledgers, and only Alchemy's counts.** Wrangler applied 0001–0009 and recorded them in `d1_migrations`; on adoption Alchemy copied that history into its own `__alchemy_migrations` and has applied every migration since, leaving `d1_migrations` frozen at 0009.
So `wrangler d1 migrations list codesplitter-db --remote` shows everything after 0009 as pending though it's all applied.
Never run `wrangler d1 migrations apply --remote`: it would run those again and fail partway.
New migrations go in `migrations/` and the next `rustybuns deploy` applies them.
To see what's applied:

```sh
npx wrangler d1 execute codesplitter-db --remote --command "select name, applied_at from __alchemy_migrations order by id"
```

cd apps/codesplitter

To put a real coding agent (claude, codex, pi or opencode, installed and logged in) on a file: it edits a copy on disk, and its edit is diffed back into line ops under its own name.

After the last run their version is kept and the conflicts are printed.

```sh
bun agent.ts --harness claude --url http://127.0.0.1:PORT --cookie 'rb_token_PORT=TOKEN' \
  --as agent-claude --repo owner/name --path src/app.ts --task "add a doc line to every function"
```

Each CLI brings its own login and model.
`--model` is passed straight through.

| Harness | Install | Login / model |
|---|---|---|
| `claude` | `npm i -g @anthropic-ai/claude-code` | `claude` once to log in |
| `codex` | `npm i -g @openai/codex` | `codex login`, or a custom provider in `~/.codex/config.toml`. Runs in its workspace-write sandbox |
| `pi` | `npm i -g @earendil-works/pi-coding-agent` (1.x; the old `@mariozechner` package is too old for the flags used here) | Defaults to Google, so pass `--model provider/id` (e.g. `anthropic/claude-sonnet-4-5`) with that provider's key in the env, or log in with `/login`. opencode's free tier refuses pi |
| `opencode` | `npm i -g opencode-ai` | `opencode auth login` and a `--model provider/id` from that provider. The free `opencode/*` models refuse runs with codeSplitter' locked-down permissions (no shell), so they don't work here |

A run's edit doesn't land on main as the agent writes it.
The agent works on a branch of its own, `agent-run-<id>`, and when it ends its batch shows on main's file page as a ghost diff: what it takes out struck through, what it puts in as grey rows, with a countdown.
When the clock runs out (8 seconds, `AGENT_REVIEW_MS`; `0` writes main directly as before), the batch merges into main by itself.
While it's on screen the landing waits; editing one of its lines, or Hold, stops the clock until you Accept; Reject throws it away, and each stretch can be left out alone.
Where someone changed a line on main meanwhile, their version stays and the line gets a small "kept yours" mark showing what the agent wanted.
A batch touching build or deploy files, or one the repo's required checks hold, waits for an Accept.
Come back to the page after a while away and a bar steps you through what changed meanwhile.
The crew sees the same waiting batch on the file and their reading it counts too: they can Hold it, while Accept, Reject and leaving a stretch out stay the owner's.
Anyone else who can read the file sees the ghost diff with no controls, with private lines blank (`GET /api/repos/:o/:r/agents/waiting?path=`).

> **⚠️ Super experimental, run at your own risk.** Coding agents run real CLIs that can edit files and run shell commands, and hosted runs spend your API keys.
> They're off by default on Cloudflare: a deploy only includes them when you set `CODESPLITTER_AGENTS=1`.
> Their keys come from 1Password, like the accounts secrets, so there's nothing else to export.

On Cloudflare a Worker is a V8 isolate: it has `node:fs` now, but it can't start the agents' CLIs (claude, codex, pi and opencode are native programs that run shell commands).
So when `AGENT_SANDBOX` is bound (deploy with `CODESPLITTER_AGENTS=1`), the file page's Agent button (`POST /api/repos/:o/:r/agents`, or `bun agent.ts ... --hosted`) runs the agent in a container instead.
Each run starts its own container (`sandbox/Dockerfile`: every CLI plus a small server), hands it the file, and stops it when the agent is done, so nothing bills while idle; `AGENT_SANDBOX` caps it at two at once on the `basic` size.
The CLIs log in with these secrets, read through varlock from the `codesplitter` vault: `ANTHROPIC_API_KEY` (`op://codesplitter/anthropic/api-key`; never a Claude subscription login, which is for your own use, #559), `OPENAI_API_KEY` (`openai/api-key`), `CODEX_API_KEY` (`codex/api-key`).
Each is optional: make the items for the harnesses you use, and the rest stay unset.
Containers need the Workers Paid plan.
A container can't reach the host, so it works with accounts on, and it needs them: hosted runs bill the site's keys, so only an owner listed in `ADMINS` can start one, and with aliases anyone could claim an admin's handle.
Without `BETTER_AUTH_SECRET` the deploy refuses `CODESPLITTER_AGENTS=1` and the route answers 501.
Each run's container only gets its own CLI's keys.
Nor can it go just anywhere (#681): it starts with the internet off, and its HTTP and HTTPS go through the Worker's `EgressGate` (`src/egress.ts`), which lets out only the run's CLI's API (`api.anthropic.com`, `api.openai.com`, and `models.dev` for opencode), GitHub when it has a `GH_TOKEN`, and for the dependency doctor's runs the repo's git remote, npm's and yarn's registries and any the repo's `.npmrc` names.
A cut's tests get nothing.
Anything else gets a 403 naming the host.
On GitHub a hosted agent is nobody until its owner says otherwise: on the dig panel, the bot button on one of their linked GitHubs (`POST /api/github/agent {id|null}`) makes that one the account their agents work as, handed to each run's container as `GH_TOKEN` and `GITHUB_TOKEN`.
Link a bot account and pick it, and the agents' clones and API calls stay apart from yours; the GitHub you dig as is never passed on unless you pick it here too.

### Search across repos (Cloudflare)

Off by default.
Search in one repo is its own `RepoSearch` Durable Object (FTS5).
Across repos, without more, it fans out to at most 50 repos you can see, yours first, then the most recently committed, so a repo past those is missed.
Deploy with `CODESPLITTER_VECTORS=1` and the Worker gets one Vectorize index across every repo (`codesplitter-vectors`, 384 dimensions, with metadata indexes on `repo` and `pub`) and Workers AI to fill it (#636).
Each commit embeds its file with `@cf/baai/bge-small-en-v1.5`, 40 lines a chunk, up to 16 chunks a file (FTS5 still has all of it), tagged with its repo and whether that was public.
A search embeds the words, takes the nearest chunks among public repos and the caller's own, checks against D1 that the caller may still see each repo, and asks the 10 nearest repos' FTS5: their hits come first, then the nearest chunks of files those didn't name.
Before anything's embedded it falls back to the fan-out, as the desktop always does (it has no Vectorize).
A repo made private disappears from other people's searches at once, since D1 decides; one made public is found across repos once the hourly cron has re-tagged its chunks.
The cron embeds up to 200 files an hour that the index doesn't have as committed: everything from before the flag, re-tagged repos, and any embed that failed (`repo_search.stale` counts them).
`POST /api/admin/scale/search-embed` runs one round of that by hand.
A deleted file or repo takes its vectors with it.

Cost: Workers AI's free 10,000 neurons a day embed roughly 5M tokens, and Vectorize on Workers Paid includes 10M stored dimensions (about 26,000 chunks) and 50M queried a month, past which it's $0.05 per 100M stored and $0.01 per 1M queried.
The first backfill is the big spend: about one chunk per 40 lines of every committed file.

### Hosted deploys

Off by default.
Deploy the site with `CODESPLITTER_DEPLOYS=1` and accounts on (`BETTER_AUTH_SECRET`), and an owner listed in `ADMINS` can store deploy keys in the repo's Deploy panel, one per provider the stack's targets use, each scoped rather than global:

- **Cloudflare** (`targets.edge`): an API token with Workers Scripts edit on one account (plus D1 and R2 edit if the app binds them), and its account ID.
- **Railway** (`targets.box` on Railway): a team token, scoped to one team.
- **Hetzner** (`targets.box` on Hetzner): a Cloud API token, read & write, made in the one project it deploys to.

Then Deploy, and their own commits to main if they turned that on, ship from the site instead of their machine.
Each step's output streams into the panel as it runs.
An x86 Hetzner box (`cpx`, `cx`, `ccx`) whose `native/` crates aren't committed as `native/dist/<crate>/linux-x64/` builds them in the deploy container, which has Rust (this adds to the run's time, inside its 13 minutes).
A `cax` (arm64) box's crates need Docker, which the container doesn't have: the run reads the config and refuses before it deploys anything, saying to deploy that one from the desktop.
Railway boxes build their crates in Railway's own image, so they deploy from the site as usual.

**The sealing key comes from 1Password, never your shell.** With `CODESPLITTER_DEPLOYS=1` the config turns on `experimental.wheel: "human"`, and `DEPLOY_SECRETS_KEY` is read from 1Password at deploy time through [varlock](https://varlock.dev) (the copy the rustybuns CLI ships with), behind your Touch ID, straight into the Worker's secret.
Once:

1. Install the 1Password CLI (`brew install 1password-cli`) and turn on Settings → Developer → "Integrate with 1Password CLI" in the 1Password app.
2. In a vault named `codesplitter`, make a Password item named `DEPLOY_SECRETS_KEY` whose password is 32 random bytes in base64 (`openssl rand -base64 32`).
   Elsewhere?
   Point `DEPLOY_SECRETS_KEY_OP` at its reference (1Password's "Copy Secret Reference").
3. `rustybuns generate` writes `.env.schema` (names and the reference, no values).
   Commit it.

**Rotating it.** Changing the item alone would orphan every stored key (and each repo's kept Alchemy state).
Instead:

1. Make a Password item `DEPLOY_SECRETS_KEY_OLD` holding the current key, then put a new one (`openssl rand -base64 32`) in `DEPLOY_SECRETS_KEY`.
2. Deploy.
   Everything sealed still opens, under either key.
3. On the admin page (the gauge in the header), press **Re-seal** under Deploy keys: every key and every repo's state is sealed under the new key.
   Anything that opened under neither is named, not dropped.
4. Delete the `DEPLOY_SECRETS_KEY_OLD` item and deploy again.

- **Write-only.** Only the owner sets, replaces or removes a key (`PUT|DELETE /api/repos/:o/:r/deploy/key/:provider`, `cloudflare`, `railway` or `hetzner`; Cloudflare's without one).
  The API never returns it: it shows who set it, when, and its last 4 characters.
  It's sealed with AES-GCM under `DEPLOY_SECRETS_KEY`, bound to its repo and provider, in D1.
- **Unsealed into one run.** Each repo has a `DeployRunner` Durable Object, so one deploy at a time; each run starts its own container (`deploy-sandbox/Dockerfile`: git, bun, node and a small server) with the keys in its env (`CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID`, `RAILWAY_API_TOKEN`, `HCLOUD_TOKEN`, whichever are stored), then destroys it.
  A run gets 13 minutes, inside the 15 a Durable Object alarm may take.
  It's a separate image and binding from `AGENT_SANDBOX`: agent containers never see a deploy key.
  The keys are scrubbed from the run's output, even split across two pieces of a stream.
- **Only the hosts it needs** (#681).
  The container starts with the internet off, and its HTTP and HTTPS go through `EgressGate` (`src/egress.ts`), an entrypoint of the Worker that passes a request on only to the repo's git remote, the package registries (npm's and yarn's) and the API of each provider it holds a key for (`api.cloudflare.com`; Railway's `backboard.railway.com` and `storage.railway.app`; `api.hetzner.cloud`), and answers anything else 403 with the host's name.
  The runtime reads the HTTPS with a CA of its own that the image trusts at start.
  Known limits: a Hetzner deploy SSHes to its new server, an address nobody knows before the run, so a run holding a Hetzner key keeps other ports open (its HTTP and HTTPS are still gated); and an install that fetches from anywhere else (a dependency straight from GitHub, a postinstall that downloads a binary) is refused, so the deploy fails naming the host.
- **The same stack each time.** The container forgets, so the repo's Alchemy state is kept by its `DeployRunner` between runs, sealed under `DEPLOY_SECRETS_KEY` (it holds the app's secrets), and put back before the next deploy.
  Without it each deploy would make a new Worker under a new name.
- **Only a person ships.** The owner's button or the owner's own commit; never an `agent-*` handle.
  Refused in alias mode, where anyone can claim a handle.
  Every hosted deploy is in the log with its keys' last 4.
- **Only the owner's code, or code they read** (#646).
  The keys run whatever is on main, so a hosted deploy walks the commits the deploy would clone back to the owner's last approval (`src/deploy-review.ts`).
  Each has to be the owner's own: their commit of a file nobody else edited since its last commit (the file's Durable Object records who did).
  Anything else (a crew or agent commit, the owner's commit of a file with someone else's edits in it, a merge, a mirror's or an import's commits) holds the deploy: the button answers 409, an owner's commit doesn't ship, and the Deploy panel lists what's waiting, shows the diff (`GET /api/repos/:o/:r/deploy/review`) and offers **Approve and deploy**, which approves main's tip (`POST .../deploy {approve: sha}`) and everything before it.
  The runner checks again just before it unseals the keys, and fails the run unless the clone is the very commit it checked.
  Desktop deploys run the same code with the logins on the owner's machine, so they're held the same way (#682): same review, same panel, and the clone has to be the commit that was checked.

What it protects against: crew can change code but can't see keys or deploy targets, and their code only reaches a key once the owner has read it and approved it.
Agents have no keys; code a prompt injection plants waits on a branch for a person.
Agents are on separate branches, containers and CLI keys, and no agent commit deploys.

### Checks in a container (Cloudflare)

Off by default.
Checks that run here are queued for a runner to claim (`src/checks.ts`).
On the desktop the app is that runner (#750): it drains its own queue in-process as soon as checks are queued, and on its 5-minute cron for any left over, one run at a time per repo, in a temp dir on your machine, so there's no `scripts/runner.ts` to start by hand.
On Cloudflare a Worker can't run a test suite, so without a runner of your own the runs wait and are cancelled after 6 hours.
Deploy with `CODESPLITTER_CHECKS=1` and they run in containers instead (`src/ci-runner.ts`): a `CiRunner` Durable Object per repo claims each queued run through the same `claimRun` as any runner, so one run at a time per repo, one per alarm, each in a fresh container (`deploy-sandbox/ci.Dockerfile`: git, bun, and the deploy image's small server) that's destroyed when the run ends.
It clones the run's commit, or main with a branch's files laid over it, runs the check's command, streams the log, and reports.
The container gets no secrets at all, starts with the internet off, and reaches only the repo's git remote and npm's and yarn's registries through `EgressGate` (#681).
A run gets 13 minutes (it's in an alarm).
A newer commit cancels the runs still queued on an older one, and each run counts against the `checks` rate limit, charged to the repo's owner: 30 an hour by default, admins exempt, tunable on `#/admin/limits`.
Its minutes (rounded up, the first taken as it starts) come off the site-wide `containers` budget, 600 a day, which admins' runs count against too.
One over either is cancelled before a container starts, saying so.
No Rust and no Docker in the image, so checks that need them belong on the desktop or a runner of your own.

What it costs (Containers on Workers Paid, priced 2026-10-11, [Cloudflare's pricing](https://developers.cloudflare.com/containers/pricing/)): a `basic` instance is 1/4 vCPU, 1 GiB and 4 GB of disk, billed per 10 ms while it runs, memory and disk as provisioned, CPU as used: $0.0000025 per GiB-second, $0.000020 per vCPU-second, $0.00000007 per GB-second.
A 5-minute run at full CPU is about $0.0023 (memory $0.00075, CPU $0.0015, disk $0.00008), and a full 13-minute one about $0.006.
The plan includes 25 GiB-hours, 375 vCPU-minutes and 200 GB-hours a month, about 300 five-minute runs.
`maxInstances: 2` caps the worst case: two containers busy around the clock is about $41 a month before the included usage.
The clone and installs are egress (1 TB a month included).
To turn it off, deploy again without the flag: the binding goes.

### CI for your public repo, on your own machine

The setup (#978): mirror the public GitHub repo into the desktop app on a machine you own, and set its checks to run `here` or `both`.

```
 GitHub (public repo)                 your machine
 ├─ main, your branches ──mirror──▶  codeSplitter desktop ── runs checks in-process
 └─ fork PRs  ✗ never mirrored         (listens on 127.0.0.1 only)
```

What the code backs up:

- **Fork PRs can't get in.** A mirror's sync fetches upstream's default branch (`refs/heads/<branch>`), and opening one of upstream's other branches fetches `refs/heads/<ref>`; nothing fetches `refs/pull/*`, where fork PRs live (`src/mirror.ts`).
  A fork's `.github/workflows` edit never reaches your machine, and `.github/` means nothing here anyway: what runs comes from `codesplitter.ci`, package.json's scripts, or a required check's `command` (`src/checks.ts`).
- **Nothing listens.** The desktop binds 127.0.0.1, and the mirror is outbound git.
  A runner of your own pulls its work too (`scripts/runner.ts`, `POST …/checks/claim`): another box can join with no open port of its own, as long as it can reach the site.
- **Your hardware.** Checks run with whatever the machine has: Rust, Docker, a big disk, all night.

The caveats:

- **Merged code runs at home.** Review is the gate, so read what you merge.
  A check gets none of your logins (#1010, `src/check-env.ts`): the desktop's queue and `scripts/runner.ts` run the clone and the command with only `PATH` and the locale from your environment, an empty `HOME` and `TMPDIR` of their own, and `CI=1`, so no `gh`, `wrangler`, npm or cloud token, and no SSH agent.
  They still run as you, with your package caches, unless you give them a sandbox user: make a standard macOS user with no logins, allow `$USER ALL=(cs-checks) NOPASSWD: ALL` in `/etc/sudoers.d/cs-checks`, and set `CODESPLITTER_CHECKS_USER=cs-checks` for the desktop (or `--user cs-checks` for a runner); every run then goes through `sudo -n -u cs-checks`, in `/tmp`, with umask 000 so the app can still clean up.
  Turn on the pin (the pin button by "Checks run", or `PUT …/checks/settings {pinned: true}`) and only the required checks with a `command` in the settings run: `codesplitter.ci` and package.json's scripts at the commit are ignored, a run queued without a command from the settings is cancelled at the claim rather than falling back to `bun test`, so a merged edit can't change the job on your machine.
- **The mirror isn't one-way.** It pushes this copy's commits upstream, never forced.
  That's a way out, not a way in, but if you want codeSplitter never to write to GitHub, don't commit to main here.
- **Merged main runs here too.** When a sync takes upstream's commits onto main (a fast-forward, a merge or a re-base), the repo's checks queue here on main's new tip, as `upstream` (#1008), beside GitHub's results for it.
  A sync that only pushes this copy's commits queues nothing: they were checked when they were made.

Still missing: a pull-only mirror (#1006).

## Conventions

Most merge conflicts here start on one hot line that two branches both grew ([docs/merge-solutions.md](docs/merge-solutions.md), §5).
These keep growth to whole lines, which merge as plain inserts (#935):

- **One item per line, with a trailing comma,** for objects, types and import lists that grow: the doctor's `Settings`, `Report` and `Update` (`src/deps.ts`), the imports in `src/worker.ts`, the doctor's save body in `src/client.html`.
- **One sentence per line** in README.md, REFERENCE.md and the docs.
  It renders the same.
  A list item's later lines sit indented under its text.
- **One setting, one declaration.**
  The doctor's settings each have a line in `FIELDS` (`src/deps.ts`), and the SQL, the reader, the checks and the API reference are built from it.
- **Migrations are named for when they were written,** `YYYYMMDDHHMMSS_name.sql` in UTC, not the next number, which two branches can both take.
- **A feature is its own file** in `src/features/`, built into `features.json`.
- **A file says its own Layout row** on its first line, `// Layout: what it is`, and `bun run layout` builds the table below from those (`layout.ts`). Two branches that each add a row and collide in the table settle it by running it again.
