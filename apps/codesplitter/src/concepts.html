concepts

Use the AI on the real work.

A swarm of agents doesn't jam because the agents aren't smart enough. It jams at the same few deterministic points: who has the file, whose copy is stale, what merges, which tests to run. codeSplitter takes those points over with plain code, so they unclog, and your AI spends its tokens on the feature. It still hooks in wherever you want a judgement call.

The road a change takes

Every change, an agent's or a person's, goes down the same road. Each stop is deterministic: same inputs, same answer, no model, no tokens. The dashed ones are where your AI can say yay or nay.

01 / branch

Artifacts

A branch is a real git repo, made in milliseconds. A thousand agents can each have one.

On its own, every copy starts drifting from the others the moment it's made.

02 / coordinate

Durable Objects

Each file's lines live in one place, on a tiny computer every agent talks to. Edits land in order, line by line, so nobody fights over a file and nobody waits on someone else's copy.

Test lanes: not every test, every time

Running every test on every change is how a swarm waits on its slowest suite. Ester gives each set of tests a cadence instead.

LaneRunsFor
alwaysevery change that touches its pathsthe tests you never want to go without
oftenevery Nth change, and at every release; the skipped ones are owedthe slow ones that add up: stress runs, the end-to-end journey
releaseonly when a release is cutwhat you don't care about until then: the iOS app, two days before the preview
busno tests per change. Changes take a seat, and when it's full (or a release is cut) the bus leaves: one big pass over all of them, an AI's if the lane has no commanddocs, copy, the long tail nobody tests by hand

Write the road down

A repo keeps its road in codesplitter.pipeline.json at the top of main. Without one: no hooks, one lane that tests everything.


    
Then ask what a change does, from wherever you work. The same plain answer each time.


# CLI
codesplitter get_pipeline --owner you --repo lab \
  --files src/app.ts,docs/guide.md

# API
GET /api/repos/you/lab/pipeline?files=src/app.ts

# try one before you commit it
POST /api/pipeline {"pipeline": {...}, "change": {"files": [...]}}

# MCP, and code mode: the tools get_pipeline, plan_pipeline

      
The answer lists every stop, the hooks that are on, and each lane's call (run, skip, board or depart), with the counts to send with the next change. The API reference · MCP

  


  
Why the AI goes around the stops

  
Whether two edits touch the same line, or whether a red check was already red on main, is a lookup, not a judgement. A model would spend tokens and minutes on it, and every agent behind it waits. So the lookups are code, and the hooks hand an AI or a person only what is truly a judgement call: is this change right, is it ready, should it ship.
