Code mode: four tools, one program

codeSplitter's MCP server has 138 tools. Listing them all puts every schema in the agent's context before it does anything, and every call hands a whole answer back through the model: a 300-line file comes back with every line, every time. In code mode the server lists four tools instead: search_tools and describe_tools find and explain the rest on demand, execute runs a JavaScript program the agent writes, and call_tool is the door to the risky ones. The file's lines stay in the program; only what it returns comes back.

finally { await tools.release_claim({ owner, repo, path, body: { id: c.id } }); }

A program that worked can be saved by name (save_program) and rerun with new input, so the next agent doesn't write it again.

WebMCP: the page hands over its own buttons

An agent driving a browser usually works by looking: take a screenshot, find the button, click, take another to check. A screenshot costs roughly width × height / 750 tokens on Claude, so a 1280 × 800 look is about 1,400 tokens, and it can't be searched or diffed. With WebMCP (document.modelContext), the page registers its actions as tools, and an agent calls them and reads a small JSON answer instead.

  • If you can click it, your agent can call it. Every ⌘K palette command on the page you're on becomes a tool (share_lines, commit_this_file, merge_a_branch…), plus current_page, open_page, list_files, read_file, the line-picking tools and list_conflicts / settle_conflict.
  • Only this page's tools. They're registered again on every route, so an agent on a file page sees the file's commands and not the admin pages'. Fewer tools listed is fewer tokens, the same idea as code mode.
  • As you, with nothing to hand over. The tools run in your signed-in page, so the agent never gets a token or a password. Commands that ship code or can't be undone are marked destructiveHint, so your agent's client can ask you first.

Three ways in, cheapest first

The CLI

One shell line, an answer sized for a terminal. The prompt we hand agents (/agent.md) puts it first. In this repo, agents made 62,749 shell calls this month against 774 on-demand tool loads.

MCP, in code mode

Four tools listed, one program per job, a small answer back. For agents with no shell, or work across many files.

WebMCP

Only for what needs your signed-in page: it acts as you, so you see what it does as it does it.

The tokens we save buy checks, and the checks are built in

Context an agent doesn't spend on plumbing goes to reading the diff, running the test and reviewing its own change. And making the agent this capable was only worth it with guard rails it can't talk its way past:

  • A program has no network. It runs in a Worker of its own with globalOutbound: null; its only way out is the tools.
  • It acts as the token that ran it, and never sees the token. A read token's program can read and not write; rate limits apply as usual.
  • Risky tools aren't callable from a program. Anything that ships code, changes who can get in or see what, or can't be undone goes through call_tool, so the person is asked.
  • Mistakes fail before anything runs. A program naming a tool that doesn't exist is refused at once, and every call's arguments are checked against its schema.
  • Hard limits. 100 tool calls, 20 seconds and 20,000 characters back per program; 64,000 characters of code.

How we measured, and what we haven't

  • Code mode: bun test test/codemode.test.ts in apps/codesplitter prints both comparisons on every run (run on 27 October 2026). It counts tokens as characters ÷ 4, a common rough rate, on the exact JSON that goes over the wire.
  • Sessions and cache: the token ledger, every assistant turn's usage from 2 to 27 October 2026, 1,490 commits on main over the same days.
  • Screenshots: an estimate from the published image-token rate, not a measured run.
