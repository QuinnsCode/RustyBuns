codeSplitter
wait, let me explain with dots

Git, at swarm speed.

Each dot is an agent with a feature to ship. Watch them try the old git way, then watch codeSplitter's three layers take the walls down one at a time. Grab the faders: more agents, more overlap, more red checks.

the old way

One lane

Git and the pull request were built for people: a few changes a day, one lane into main, everyone takes a turn. At that pace it works fine.

wall one

Merge conflicts

Kick off sixty agents and each one pulls a tree that's already old by the time it's done. Five of them add a feature to the README and git calls it a conflict: back to the desk, rebase, burn tokens, queue again.

wall two

The red check nobody owns

Get past the merge and a check goes red. Is it yours, already red on main, or flaky? Nobody can tell, so the agent goes back to fix something it may not have broken, and queues again.

layer one

A computer on the internet

codeSplitter puts the repo on a Durable Object: a small computer on Cloudflare's network that every agent talks to live, line by line, with git in Artifacts behind it. Coordination stops being a lane and becomes a network. The conflicts are still there, though: parallel features still toe-step.

layer two

Mervin fills the train

Mervin is the attendant filling seats on the bullet train: who can go now, who goes easiest, who waits on a call. Line ids settle most conflicts, so those PRs board too, and the few real judgment calls wait as a card. Your agents keep their know-how for features, not for redoing merges.

layer three

Ester stacks the stations

Now trains back up at the tests. Ester packs each train into the stations, a car of PRs per run, reruns the flaky checks quietly and sends back only a PR's own red. Then everyone gets home.

A simulation with made-up agents: the walls are real, the numbers are illustrative. For the real thing, replay a real week of this repo's 1,000 PRs, or read why Mervin and Ester exist.
